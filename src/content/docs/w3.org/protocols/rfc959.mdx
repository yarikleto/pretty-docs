The File Transfer Protocol (FTP) was designed in an era when computers disagreed about almost everything — how to represent text, how to organize files, even how many bits made up a byte. Its data transfer system had to bridge all of that. Rather than choosing one format and forcing everyone to use it, FTP lets the sender and receiver **negotiate** how data should be represented, structured, and transmitted.

This article covers Section 3 of RFC 959, which defines the three independent parameters that together describe any FTP data transfer. Think of them as three questions that must be answered before a single byte moves:

1. **What language are we speaking?** (Data Type)
2. **How is the content organized?** (Data Structure)
3. **How do we ship it?** (Transfer Mode)

## The Three Dimensions of a Transfer

Every FTP transfer is defined by three independent choices, set with the `TYPE`, `STRU`, and `MODE` commands before the transfer begins. Each choice is orthogonal — changing the data type does not constrain which structure or mode you can use.

The defaults — ASCII type, File structure, Stream mode — work for simple text transfers between similar systems. But transferring a compiled executable from a mainframe to a Unix workstation? You would need to change at least the type (to Image) and possibly the structure (to Record) to avoid mangling the data.

## Data Types

Think of data types as **languages** — the sender and receiver need to agree on which one they are speaking. If the sender transmits a file as ASCII text but the receiver tries to interpret it as raw binary, the result is garbled data. The `TYPE` command sets this agreement before any transfer begins.

### ASCII Type

**ASCII** is the default data type, and the one you will encounter most often with text files. When a file is transferred in ASCII mode, FTP performs a crucial translation: the sender converts its native line endings to a canonical format (CRLF — carriage return followed by line feed), and the receiver converts CRLF back to whatever its operating system expects.

This matters because operating systems disagree about line endings. Unix uses a single line feed (LF). Classic Mac OS used a carriage return (CR). Windows uses both (CRLF). Without this normalization, a text file transferred from Unix to Windows would appear as one enormous line.

ASCII type also supports an optional **second parameter** for vertical format control — how form feeds, vertical tabs, and other formatting characters should be interpreted. In practice, the two sub-options (Non-print and Telnet) are rarely specified; Non-print is the default and simply means "no special formatting."

### EBCDIC Type

**EBCDIC** is the ASCII type's counterpart for IBM mainframe systems. Where ASCII type uses the ASCII character set as the transfer representation, EBCDIC type uses the EBCDIC character set. It serves the same purpose — text transfer with line-ending normalization — but for environments where EBCDIC is the native encoding.

Like ASCII, EBCDIC supports the same vertical format control sub-options. Unless you are transferring files to or from an IBM mainframe, you will never encounter this type.

### Image Type (Binary)

**Image type** — commonly called **binary mode** — transfers data byte-for-byte with no conversion whatsoever. The file is treated as a continuous stream of bits, packed into 8-bit bytes for transfer, and stored without any transformation at the receiving end.

This is the type you want for anything that is not plain text: images, executables, compressed archives, PDFs, database files. Any byte-level modification during transfer would corrupt these files. A JPEG image has no "line endings" to normalize — every byte is meaningful data.

### Local Type

**Local type** exists for systems where the fundamental storage unit is not an 8-bit byte. The sender specifies a **byte size** (the number of bits per logical byte on the local system), and data is transferred using that byte size. This accommodated machines with 36-bit words or other non-octet architectures. On modern systems (which universally use 8-bit bytes), Local type with a byte size of 8 is functionally identical to Image type.

:::note[Why this matters]
The single most common FTP mistake is transferring a binary file in ASCII mode. Because ASCII mode rewrites bytes that happen to match line-ending characters (CR, LF), a binary file transferred as ASCII arrives corrupted — images display with artifacts, executables crash, archives fail to decompress. Most modern FTP clients default to binary mode precisely to avoid this. If you ever see a transferred file that is "almost right" but slightly broken, check the transfer type first.
:::

{`   3.1.1.  DATA TYPES

      Data representations are handled in FTP by a user specifying a
      representation type.  This type may implicitly (stripping line
      endings) or explicitly (as in local type) define a byte size for
      interpretation which is referred to as the "transfer byte size."

         ASCII TYPE

            This is the default type and must be accepted by all FTP
            implementations.  It is intended primarily for the transfer
            of text files, except when both hosts would find the EBCDIC
            type more convenient.

            The sender converts the data from an internal character
            representation to the standard 8-bit NVT-ASCII
            representation (see the Telnet specification).  The receiver
            will convert the data from the standard form to his own
            internal form.

            In accordance with the NVT standard, the <CRLF> sequence
            should be used where necessary to denote the end of a line
            of text.

         EBCDIC TYPE

            This type is intended for efficient transfer between hosts
            which use EBCDIC for their internal character representation.

            For transmission, the data are represented as 8-bit EBCDIC
            characters.  The character code is the only difference
            between the functional specifications of EBCDIC and ASCII
            types.

         IMAGE TYPE

            The data are sent as contiguous bits which, for transfer,
            are packed into the 8-bit transfer bytes.  The receiving
            site must store the data as contiguous bits.

         LOCAL TYPE

            The data is transferred in logical bytes of the size
            specified by the obligatory second parameter, Byte size.
            The value of Byte size must be a decimal integer; there is
            no default value.`}
</RfcToggle>

## Data Structures

Data types define how to **interpret** bytes. Data structures define how to **organize** them. Think of it this way: the type tells you whether the bytes represent text or binary data, while the structure tells you whether those bytes form one continuous stream, a sequence of records, or a set of indexed pages.

The `STRU` command sets the structure before a transfer. Most modern transfers use File structure (the default), but understanding all three helps explain why certain FTP features exist.

<StructureCard

<SourceRef section="3.1.2" quote="In addition to different representation types, FTP allows the structure of a file to be specified." />

The key insight is that **structure and type are independent**. You can transfer ASCII text in Record structure (common on mainframes that store text files as records) or Image data in File structure (the typical modern case). The three structure options exist not because FTP was over-designed, but because the protocol had to accommodate fundamentally different ideas about what a "file" is.

## Transfer Modes

Transfer modes answer the final question: **how do we ship the data?** The data type says what the bytes mean, the structure says how they are organized, and the mode says how they are packaged for transmission over the data connection. The `MODE` command selects one of three options before a transfer begins.

### Stream Mode

**Stream mode** is the default and by far the most common. Data is transmitted as a plain stream of bytes with no framing added by FTP itself. The end of a file is signaled by the sender closing the data connection — simple and efficient.

For File structure, closing the connection is all that is needed to mark the end. For Record structure, a two-byte control code (0xFF followed by a descriptor byte) is inserted into the stream to mark end-of-record (EOR) and end-of-file (EOF) boundaries. If the actual data contains 0xFF, it is escaped by sending 0xFF twice.

Stream mode is efficient because it adds **zero overhead** for the most common case (File structure transfers). There are no headers, no block boundaries, no compression — just raw data flowing from sender to receiver. The downside is that if the connection drops mid-transfer, there is no way to know how much data was lost or to resume from where it left off.

<SourceRef section="3.4.1" quote="The data is transmitted as a stream of bytes." />

### Block Mode

**Block mode** wraps the data in a series of blocks, each preceded by a three-byte header. This header tells the receiver exactly how many data bytes follow and provides flags that describe the block's role in the transfer.

<BlockHeader />

The **descriptor byte** uses individual bits as flags:

| Bit Value | Flag | Meaning |
|-----------|------|---------|
| 128 (0x80) | EOR | End of record — this block is the last in the current record |
| 64 (0x40) | EOF | End of file — this block is the last in the file |
| 32 (0x20) | Errors | Suspected errors in the data (the block may be unreliable) |
| 16 (0x10) | Restart | This block contains a restart marker, not file data |

:::caution[Important]
These values are **bit flags**, not mutually exclusive enums. They combine by addition (or bitwise OR). A descriptor value of **192** means both EOR and EOF are set (128 + 64) — the block is simultaneously the last in its record and the last in the file. The remaining bits (8, 4, 2, 1) are reserved and should be zero.
:::

The **byte count** (16 bits) gives the exact number of data bytes following the header, allowing the receiver to find the next block header without scanning the data. This makes block mode **restartable** — if a transfer fails, the restart marker flag lets the sender insert checkpoint information that both sides can use to resume from a known point rather than starting over.

<SourceRef section="3.4.2" quote="The block header consists of the count field, and descriptor code." />

<RfcToggle section="3.4.2" label="See original RFC text for Block Mode">
{`   3.4.2.  BLOCK MODE

      The file is transmitted as a series of data blocks preceded by
      one or more header bytes.  The header bytes contain a count
      field, and descriptor code.  The count field indicates the
      total length of the data block in bytes, thus marking the
      beginning of the next data block (there are no filler bits).
      The descriptor code defines:  last block in the file (EOF)
      end of record (EOR), restart marker (see the Section on
      Error Recovery and Restart) and suspected errors in data
      block.

      The data header consists of three bytes.  Of the 24 bits of
      header information, the 16 low order bits shall represent
      byte count, and the 8 high order bits shall represent
      descriptor codes as shown below.

         Block Header

            +----------------+----------------+----------------+
            | Descriptor     |    Byte Count                   |
            |         8 bits |                      16 bits    |
            +----------------+----------------+----------------+

         The descriptor codes are indicated by bit flags in the
         descriptor byte.  Four codes have been assigned, where
         each code number is the decimal value of the
         corresponding bit in the byte.

            Code     Meaning

             128     End of data block is EOR
              64     End of data block is EOF
              32     Suspected errors in data block
              16     Data block is a restart marker

         With this encoding, more than one descriptor coded
         condition may exist for a particular block.  As many bits
         as necessary may be flagged.

         The restart marker is embedded in the data stream as an
         integral number of 8-bit bytes representing printable
         characters in the language being used over the control
         connection (e.g., default--NVT-ASCII).`}
</RfcToggle>

### Compressed Mode

**Compressed mode** applies a simple run-length encoding scheme to reduce the amount of data transmitted. It is defined in the RFC but rarely used in practice — modern file compression (gzip, zlib) is far more effective and is typically applied before transfer, not during it.

The compression scheme encodes data bytes into three types of output:

1. **Regular data** — a byte with bit 7 clear and bits 6-0 giving a count (1-127), followed by that many data bytes transmitted verbatim. This is used for sequences of non-repeating data.
2. **Replicated data** — a byte with bit 7 set and bit 6 clear, where bits 5-0 give the repeat count, followed by a single data byte to be replicated that many times. This compresses runs of identical bytes (e.g., long strings of spaces or null bytes).
3. **Filler bytes** — a byte with bits 7 and 6 both set, where bits 5-0 give a count of filler bytes to insert. The filler character depends on the data type (zero for Image, space for ASCII/EBCDIC).

Like block mode, compressed mode uses a two-byte control sequence to mark EOR and EOF boundaries within the stream.

## Example Session

Putting it all together — here is what a typical FTP data transfer looks like on the wire. The client connects, authenticates, sets the transfer type to binary (Image), enters passive mode, and retrieves a file.

<FtpSession title="FTP Session" context="Control connection (port 21)">
<span class="syn-comment"># Client connects to FTP server</span>
<span class="syn-response">220 ftp.example.com FTP server ready</span>

<span class="syn-command">USER</span> <span class="syn-string">alice</span>
<span class="syn-response">331 Password required for alice</span>

<span class="syn-command">PASS</span> <span class="syn-string">••••••••</span>
<span class="syn-response">230 User alice logged in</span>

<span class="syn-comment"># Set transfer type to Image (binary) — no byte conversion</span>
<span class="syn-command">TYPE</span> <span class="syn-string">I</span>
<span class="syn-response">200 Type set to I</span>

<span class="syn-comment"># Request passive mode — server provides address for data connection</span>
<span class="syn-command">PASV</span>
<span class="syn-response">227 Entering Passive Mode (<span class="syn-number">192,168,1,10,195,149</span>)</span>

<span class="syn-comment"># Client opens data connection to 192.168.1.10 port 50069 (195×256+149)</span>
<span class="syn-comment"># Then requests the file</span>
<span class="syn-command">RETR</span> <span class="syn-string">report-2026.pdf</span>
<span class="syn-response">150 Opening BINARY mode data connection for report-2026.pdf (<span class="syn-number">2458624</span> bytes)</span>

<span class="syn-comment"># File data flows over the data connection...</span>
<span class="syn-response">226 Transfer complete</span>

<span class="syn-command">QUIT</span>
<span class="syn-response">221 Goodbye</span>
</FtpSession>

:::note
Notice how the three dimensions we covered all appear in this session. The `TYPE I` command sets the **data type** to Image (binary). The structure defaults to **File** (no `STRU` command needed). And the mode defaults to **Stream** (no `MODE` command needed). The PASV/RETR exchange then transfers the file as a raw byte stream over a separate data connection — exactly as Stream mode specifies.
:::
