The File Transfer Protocol (FTP) defines a standard way to move files between a client and a server over a TCP/IP network. While the protocol handles authentication, directory listing, and connection management, its core purpose is **reliable data transfer**. This article covers the three pillars of FTP data transfer: data types, data structures, and transfer modes.

## The Three Dimensions of a Transfer

When FTP transfers a file, three independent parameters define how that data moves. Think of them as three axes of a coordinate system — each choice is independent of the others:

1. **Data Type** — how to interpret the bytes (text vs. binary)
2. **Data Structure** — how the file is organized (flat, records, or pages)
3. **Transfer Mode** — how to send it over the wire (stream, blocks, or compressed)

These three choices are set independently with the `TYPE`, `STRU`, and `MODE` commands before a transfer begins.

## Data Types

FTP supports several data representations to handle the differences between operating systems. When a file is transferred, both the sender and receiver must agree on how to interpret the bytes.

**ASCII type** is the default. Text files are transferred in ASCII with line endings normalized — the sender converts native line endings to CRLF (carriage return + line feed), and the receiver converts CRLF to its native format. This ensures that a text file created on Unix (LF endings) can be read correctly on Windows (CRLF endings) and vice versa.

**Image type** (also called binary) transfers files byte-for-byte with no conversion. This is essential for non-text files like images, executables, and compressed archives, where any byte modification would corrupt the data. Most modern FTP usage defaults to binary mode since incorrect ASCII conversion can damage files that aren't plain text.

**EBCDIC type** exists for transfers between systems that use EBCDIC encoding (primarily IBM mainframes). It functions like ASCII type but uses EBCDIC as the transfer representation instead.

## Data Structures

Beyond the type system, FTP defines how data is organized within a transfer. The structure determines whether the data is treated as a continuous stream or broken into logical units.

**File structure** is the default and most common. The file is treated as a continuous sequence of bytes with no internal structure. This maps naturally to how modern operating systems handle files and is the structure used in almost all contemporary FTP transfers.

**Record structure** divides the file into sequential records. This is relevant for systems where files are inherently record-oriented (such as mainframe datasets). Each record is delimited within the data stream, allowing the receiver to reconstruct the record boundaries.

**Page structure** allows files to be transferred as independent indexed pages. Each page has a header containing its index and metadata. This structure is rarely used in practice but was designed for systems where files are stored as non-contiguous pages (like some virtual memory systems).

## Transfer Modes

The transfer mode determines how data is formatted and sent through the data connection. The mode affects framing and error recovery, not the data representation (which is handled by the data type).

**Stream mode** is the default and simplest mode. Data is sent as a continuous stream of bytes. For file structure, the end of file is indicated by the sender closing the data connection. Stream mode has no overhead and is the mode used by virtually all modern FTP implementations.

**Block mode** wraps the data in a series of blocks, each with a header containing a count field and descriptor code. The descriptor indicates whether the block is the end of a record, end of file, or a restart marker. Block mode allows the data connection to remain open between transfers and supports restart of interrupted transfers.

**Compressed mode** uses run-length encoding to compress the data before transmission. Runs of repeated bytes are replaced with a single byte and a repeat count. While this reduces bandwidth for certain types of data, modern alternatives like gzip compression at the application level or TLS compression have made this mode largely obsolete.
