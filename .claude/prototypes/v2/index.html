Data Types

FTP supports four data types that determine how file contents are interpreted during transfer. The type you choose depends on what you're sending and who's receiving it.

A

ASCII

Default type. Text files converted to 8-bit NVT-ASCII. Lines end with CRLF.

I

Image (Binary)

Raw contiguous bits, packed into 8-bit bytes. No conversion. Use for non-text files.

E

EBCDIC

For mainframe-to-mainframe transfers. Rarely used today.

FTP Data Transfer

How FTP represents, structures, and transmits file data between hosts — the three dimensions of a transfer.

Based on RFC 959, Section 3 View original | 12 min read

When FTP transfers a file, three independent parameters define how that data moves. Think of them as three axes of a coordinate system — each choice is independent of the others:

  1. Data Type — how to interpret the bytes (text vs. binary)
  2. Data Structure — how the file is organized (flat, records, or pages)
  3. Transfer Mode — how to send it over the wire (stream, blocks, or compressed)

These three choices are set independently with the TYPE, STRU, and MODE commands before a transfer begins.

The Three Dimensions of a Transfer

RFC 959, Section 3.1 — "Data representation is handled in FTP by a user specifying a representation type."

Data Types

The data type tells both sides how to interpret the bytes in transit. The most important distinction: ASCII for text (where line endings get converted) and Image for binary (where bytes pass through untouched).

Why this matters

Transferring a binary file (like a JPEG) in ASCII mode will corrupt it — the client will try to convert line endings in what are actually pixel values. This is the single most common FTP mistake.

ASCII type converts the sender's internal character representation to standard 8-bit NVT-ASCII for the wire, then the receiver converts back. Line endings are normalized to CRLF during transfer.

Image type (also called Binary) sends data as raw, contiguous bits packed into 8-bit transfer bytes. No conversion of any kind. The receiving site stores the bits exactly as received.

EBCDIC type works like ASCII but for hosts that use EBCDIC internally — primarily IBM mainframes. Local type allows specifying a custom byte size for systems with non-8-bit architectures.

Data Structures

Structure defines the internal organization of the file. Most transfers use File structure (the default) — a flat stream of bytes with no internal boundaries.

F

File Structure

No internal structure. The file is a continuous sequence of data bytes. This is the default when no STRU command is issued.

R

Record Structure

The file is made up of sequential records. Useful for systems where files have inherent record boundaries, like mainframe datasets or line-oriented text.

P

Page Structure

The file is a set of independent indexed pages, each sent with a header containing the page index, data length, and page type. Used by systems with random-access file structures like TOPS-20.

Transfer Modes

The transfer mode determines how data is packaged for transmission over the data connection. This is where the wire-level mechanics live.

Stream Mode

Stream mode is the default and simplest. Data is transmitted as a raw stream of bytes with no block boundaries. For file-structure data, the end of file is signaled by the sender closing the data connection.

For record-structure data, a special two-byte escape sequence marks record and file boundaries: the all-ones byte (0xFF) followed by a descriptor (1 for EOR, 2 for EOF).

Block Mode

Block mode wraps data in blocks, each preceded by a three-byte header. This is more structured than Stream mode and supports restart markers for resuming interrupted transfers.

Block Header Format

The descriptor byte uses individual bits as flags. Multiple flags can be set simultaneously on a single block — for example, a block can be both the end of a record and the end of a file.

Bit Value Binary Flag Meaning
128 10000000 EOR End of record
64 01000000 EOF End of file
32 00100000 Errors Suspected errors in data block
16 00010000 Restart Data block is a restart marker

Bit flags, not enums

The descriptor codes are bit flags, not mutually exclusive values. A descriptor of 192 (128 + 64) means the block is both the end of a record AND the end of the file. This is a common point of confusion.

RFC 959, Section 3.4.2 — "The block header consists of the count field, and descriptor code."

RFC 959, Section 3.4.2
3.4.2. BLOCK MODE The file is transmitted as a series of data blocks preceded by one or more header bytes. The header bytes contain a count field, and descriptor code. The count field indicates the total length of the data block in bytes, thus marking the beginning of the next data block (there are no filler bits). The descriptor code defines: last block in the file (EOF) last block in the record (EOR), restart marker (see the Section on Error Recovery and Restart) or suspect data (i.e., the data being transferred is suspected of errors and is not reliable). This last code is NOT an error indicator; it is used to indicate that the data being transferred is suspect). The descriptor code is indicated by specific bits in the descriptor byte. Four codes have been assigned, where each code number is the decimal value of the corresponding bit in the byte. Code Meaning 128 End of data block is EOR 64 End of data block is EOF 32 Suspected errors in data block 16 Data block is a restart marker With this encoding, more than one descriptor coded condition may exist for a particular block. As many bits as necessary may be flagged. The restart marker is embedded in the data stream as an integral number of 8-bit bytes representing printable characters in the language being used over the control connection (e.g., default--NVT-ASCII). +----------------+----------------+----------------+ | Descriptor | Byte Count | | 8 bits | 16 bits | +----------------+----------------+----------------+

Compressed Mode

Compressed mode applies simple run-length encoding to reduce the size of data on the wire. Each piece of data is sent as one of three types:

1

Regular data — up to 127 raw bytes, preceded by a count byte with its high bit set to 0.

2

Replicated byte — a single byte repeated N times. Two-byte encoding: count (with 10 prefix) followed by the byte to repeat.

3

Filler string — repeated padding character (space for ASCII/EBCDIC, zero for Image/Local). One-byte encoding with 11 prefix.

Example: An FTP Session

Here is a typical FTP session that sets up a binary transfer in block mode. The USER and PASS commands authenticate, then the transfer parameters are set before the file is retrieved.

FTP Session — Binary Transfer in Block Mode Control connection (port 21) 
// Connect to FTP server
220 ftp.example.com FTP server ready.

USER anonymous
331 Guest login ok, send your email as password.

PASS user@example.com
230 User logged in.

// Set transfer parameters
TYPE I              // Image (binary) type
200 Type set to I.

MODE B              // Block mode
200 Mode set to B.

STRU F              // File structure (default)
200 Structure set to F.

// Transfer the file
RETR /pub/data/archive.tar.gz
150 Opening BINARY mode data connection for archive.tar.gz
// ... data blocks with headers flow over data connection ...
226 Transfer complete.

QUIT
221 Goodbye.

Two connections

FTP uses separate connections for commands (port 21) and data transfer (port 20 or negotiated). The commands above flow over the control connection. The actual file data flows over a separate data connection established by the RETR command.
